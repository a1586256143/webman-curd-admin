# 升级 · 部署 · 发布

升级为什么不会自动生效、怎么把新版插件同步进宿主、上线部署要配什么、怎么打发布包。

---

## 1. 升级安全（覆盖同步，宿主密钥除外）

安装器策略（2026-10-15 起）：宿主已存在 `plugin/curd` 时，`composer update` /
首次 `composer require` 会**整目录删除后从包内重新整体拷贝（覆盖同步）**，顺便清掉
包内已移除的陈旧文件。唯一保留的是宿主自有的 `plugin/curd/config/keys/*.pem`
（RSA 加密密钥对，覆盖会静默破坏接口加解密，故不删也不被包内版本覆盖）。

> ⚠️ 副作用：**宿主 `plugin/curd` 下的本地改动会被覆盖抹掉**（密钥除外）。
> 想保留改动，先 `git stash` / 提交 / 迁回插件配置化，再升级。

### 1.1 覆盖边界：`composer update` 到底动哪些文件

触发链路是 composer 的 `post-package-update` → `support\Plugin::install` →
`Amcolin\WebmanCurdAdmin\Install::install()`（`src/Install.php`）。逐项边界：

| 文件 / 目录 | 会被动吗 | 条件 |
|---|---|---|
| `vendor/amcolin/webman-curd-admin/**` | **会** | composer 的本职，装的就是它 |
| `plugin/curd/**`（除 `config/keys/`） | **会（覆盖）** | 已存在即整目录删除后重拷；包内已删的文件也会从宿主清掉 |
| `plugin/curd/config/keys/*.pem` | **不动（保留宿主版）** | 宿主已有密钥文件 → 删目录时保留、拷包时排除，不碰宿主密钥 |
| 宿主 `config/curd-admin.php` | **不动** | 已存在即 `return`，只在**缺失**时才生成模板 |
| 宿主 `config/database.php` | **会**（但先备份） | 唯一例外：仅当内容仍含 `your_database` / `your_username`（webman 占位模板）→ 先备份成 `database.php.webman-db.bak` 再替换；已是自定义配置则不动 |
| `app/controller/admin/api/MyTestController.php`、`app/model/MyTest.php` | 只在**缺失**时新生成 | 已存在（含你自己改过的）→ 跳过 |
| `.env` | **不动** | 安装器完全不碰 env |

一句话：**装好之后，配置不会被 `composer update` 覆盖**。唯一会写的是还停留在 webman
占位模板的 `config/database.php`，而且**先备份后替换**。

> ⚠️ 升级后 `plugin/curd` 已是覆盖后的新版（看它即可）；`vendor/` 里是包本体。
> 想比对宿主与包的差异，用 `git diff` 或 `scripts/check-plugin-overrides.sh`。

要把新版插件文件同步到宿主，走这两步：

```bash
# ① 升级前先检查宿主 plugin/curd 有无本地改动（0=无改动，1=发现改动）
./scripts/check-plugin-overrides.sh <宿主项目根>

# ② 确认无本地改动（或已备份）后整体重拷
bash scripts/sync-plugin.sh
#    = 备份 plugin/curd → plugin/curd.bak-<时间戳>，再从 vendor 整体重拷
#    宿主 config/curd-admin.php 与 config/database.php 已存在，不会被覆盖
```

发现改动时：先 `git stash` / 提交 / 把改动**迁回插件配置化**，再升级。

> 只改了内置前端的话，用 `scripts/build-frontend.sh` 重建 dist 即可，
> 不必动 `plugin/curd` 源码。

**升级后建议再跑一次幂等安装**，补齐新表 / 新种子 / 新菜单：

```bash
php plugin/curd/install.php      # 幂等：已存在的全 SKIP
php plugin/curd/migrate.php      # 如有增量迁移文件
```

## 2. 同步清单：哪些文件属于宿主、不能覆盖

`sync-plugin.sh` 会整体重拷 `plugin/curd`，但下列内容属于**宿主专有**，
绝不能覆盖或删除（手工同步时逐条核对）：

| 文件 / 目录 | 说明 |
|---|---|
| `plugin/curd/config/keys/` | RSA 私钥（覆盖安装时**自动保留**宿主版，不会被重拷覆盖；换机需手动拷贝，丢失要重生成） |
| `plugin/curd/install-business.sql` | 宿主真实业务建表 SQL（`--business-sql` 用它） |
| `plugin/curd/public/assets/` | 宿主自己的前端构建产物（若是自行构建的版本） |
| `plugin/curd/migrations/` | 宿主的增量迁移文件（`V{n}__*.sql`）—— 同步时不要删除 / 覆盖 |
| 宿主根 `config/curd-admin.php`、`config/database.php`、`.env`、`app/` | 插件之外的宿主自有层 |

顺带一提，包 → 宿主需要同步的核心条目是：`api/Install.php`、`app/`、
`config/*.php`、`env.example`、`install.php`、`install.sql`、`migrate.php`、`public/`。

## 3. 卸载

```bash
composer remove amcolin/webman-curd-admin
# 卸载钩子 support\Plugin::uninstall → Install::uninstall() 会自动删除宿主 plugin/curd
php start.php restart
```

> 前提：宿主 composer.json 已挂载 `post-package-uninstall` → `support\\Plugin::uninstall`
> （webman 骨架默认有；huafei / clean-demo 均已配置）。删除后接口加解密 / 后台随之失效，需 restart 生效。

`config/curd-admin.php`、示例控制器 / 模型等宿主侧产物**不随插件删除**（避免误删你的
业务代码），需自行决定是否清理。

## 4. 生产部署

### 4.1 守护进程（supervisor）

```ini
# /etc/supervisor/conf.d/my-app.conf
[program:my-app]
command=php /var/www/my-app/start.php start
directory=/var/www/my-app
numprocs=1
autostart=true
autorestart=true
startretries=3
user=www-data
redirect_stderr=true
stdout_logfile=/var/log/my-app/worker.log
```

```bash
supervisorctl reread && supervisorctl update && supervisorctl start my-app
```

> 不要裸跑 `php start.php start -d`。托管后整体重启用 `supervisorctl restart my-app`
> （手动 `php start.php restart` 会杀会话进程组）。插件的 `SIGUSR1` 平滑 reload 只重启
> worker、不杀 master，与 supervisor 托管兼容，仍可用于「改配置即时生效」。

### 4.2 Nginx 反代（SPA 与 API 同域，免 CORS）

```nginx
server {
    listen 80;
    server_name admin.example.com;
    root /var/www/my-app/public;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }
    location /index.php {
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root/index.php;
        fastcgi_pass 127.0.0.1:8787;   # 与 config/process.php 的 'listen' 一致
    }
    location /app/curd/ {              # 插件内置前端（SPA history 由 PageController 处理）
        try_files $uri $uri/ /index.php?$query_string;
    }
}
```

webman 侧取真实客户端 IP 用 `connection->getRemoteIp()`，依赖 Nginx 正确透传。

### 4.3 环境与密钥（上线检查单）

- [ ] **`.env` 设 `APP_DEBUG=false`** —— 否则接口未捕获异常会把堆栈 / 表结构直接抛给前端，
      既泄漏实现细节、又拿不到统一提示；**同时它会关掉配置生成器**（见下一条）；
- [ ] **确认配置生成器已关闭**：`APP_DEBUG=false` 即默认关闭（菜单隐藏 + 路由拦截 + 接口 403）；
      想更保险可在 `config/curd-admin.php` 显式写 `'generator_enabled' => false`。
      详见 [配置参考 §4.5](03-配置参考.md)；
- [ ] **`config/exception.php` 的 `''` 键**指向
      `\plugin\curd\app\exception\CurdExceptionHandler::class`（宿主自己的 `/api` 控制器才覆盖到；
      插件路由靠插件自带配置已生效）；
- [ ] **`config/middleware.php` 的 `'@'` 组**注册 `StaticFile`；
      `ApiCrypto` 已由插件自带（`plugin/curd/config/middleware.php`，键名 `'plugin.curd'`），
      **只有宿主自建、不在插件命名空间下的 `/api` 接口**才需要在这里补一行（重复挂载安全）；
- [ ] `config/curd-admin.php` 开 `admin_require_permission => true`；
- [ ] 登录后立即修改初始管理员密码；
- [ ] `config/keys/` 独立挂载、不进 git / 不进发布产物
      （`composer require/update` 结束自动生成，缺了就 `php webman curd:crypto-key`
      或 `php plugin/curd/keygen.php`，换钥后记得 restart，前端不用重新打包）；
- [ ] 开发 / 测试 / 生产各用独立数据库，`.env` 不进 git。

细节见 [接口加密与异常兜底](14-接口加密与异常兜底.md) 与 [配置参考](03-配置参考.md)。

### 4.4 备份

| 对象 | 频率 | 方式 |
|---|---|---|
| 数据库（认证表 + 业务表同库） | 每日 | `mysqldump` 全量 + 保留 7 天 |
| `config/keys/`（RSA 私钥） | **生成即备份** | 单独加密归档，切勿丢失；丢了用 `php webman curd:crypto-key --force` 重生成（前端自动握手，无需重新打包） |
| 代码 / 前端 dist | 每次发版 | git tag + CI 产物 |

> RSA 私钥丢失不影响登录，只影响已加密的接口。

### 4.5 升级与回滚

```bash
# 升级前确认无本地改动
./scripts/check-plugin-overrides.sh <宿主项目根>
bash scripts/sync-plugin.sh          # 自带备份 plugin/curd.bak-<时间戳>
php plugin/curd/install.php          # 幂等补表 / 补种子 / 补菜单
```

回滚 = 恢复 `plugin/curd.bak-*` 后 reload；或 `git checkout <上一版本 tag>` /
composer 锁版本重装。

## 5. 发布（zip / GitHub Release）

```bash
# 本地打 zip（排除 keys / install-business.sql / release-zip.sh 自身）
./scripts/release-zip.sh 1.1.0
# → dist/webman-curd-admin-v1.1.0.zip（约 1.1M，解压即用）

# 发布到 GitHub
git tag v1.1.0 && git push origin v1.1.0
# → .github/workflows/release.yml 自动跑：
#   composer validate --strict → 全量 php -l → 前端 dist 完整性校验
#   → 关键文件存在性校验 → release-zip.sh → GitHub Release 附 zip
```

> **CI 不跑 npm**：内置前端由开发者本地 `scripts/build-frontend.sh` 构建后提交 dist，
> CI 只校验产物完整性（`index.html` + `assets/` + 文件数 > 10）。
>
> zip 包内容 = `composer.json` + `README.md` + `INSTALL.md` + `docs/` +
> `plugin/curd/` + `scripts/`；`config/keys/`、`install-business.sql` 不进包。

## 6. 与本项目 webman-huafei-platform 的关系

本包由 `webman-huafei-platform/plugin/curd` 发布而来，演进分三阶段：

| 阶段 | 做了什么 |
|---|---|
| **M1** 自包含下沉 | middleware / rbac / model / helpers / `casbin.conf` 全部内置，插件不再依赖宿主 `app\middleware`、`app\rbac`、`app\functions.php`、`app\model\CurdConfigs`；宿主业务代码零改动、行为不变 |
| **M2** 开箱即用 | `install.sql` + `api/Install.php` + `install.php` 一键建表 / 种子 / 密钥；前端 dist 内置 `public/`，`/app/curd/` 直接打开完整后台 |
| **M3** 管理面内置 | 用户 / 角色 / 个人中心下沉进插件并注册路由（宿主同名路由优先，零行为变化）；新增 `admin_require_permission` 收紧开关；路由注册改走 `curd_route()` 冲突检测（修掉「重复注册抛 Route conflict」的崩溃点）；在全新空 webman 项目上完成端到端验证 |

**M5 宿主旧副本下线**：宿主侧的 `app/middleware/*`、`app/rbac/*`、`app/functions.php`
已切到插件内置版并删除（`StaticFile.php` 是宿主自有，保留）。

> 宿主开发期两条命令：
> `scripts/release.sh` 把宿主侧改动回灌到包；`scripts/build-frontend.sh` 重建内置前端。

**huafei 宿主的 composer 现状**：`composer.json` 的 `repositories` 已清空，包也不在
packagist 上，依赖只存在于 `composer.lock`（`dev-main`，指向 GitHub 的 zipball）。
所以在这个宿主里跑 `composer update`（无论全量还是指定本包）会直接报：

```
Root composer.json requires amcolin/webman-curd-admin dev-main, found
amcolin/webman-curd-admin[dev-main] in the lock file but not in remote repositories
```

`composer install`（按 lock 装）仍可用。换句话说，**在 huafei 上 `composer update`
根本走不到安装器那一步** —— 连 `vendor/` 都不会变；要升级 `plugin/curd` 只能走
`scripts/sync-plugin.sh`。

## 7. 文档站构建与发布

文档源就是仓库 `docs/` 下的 `*.md`，`docs/index.html` 是由它们生成的**自包含单页**
（CSS / JS / 内容全内嵌，无网络依赖，双击即可打开）。

### 7.1 重新构建

```bash
cd docs
node tools/build_docs.cjs
# docs 扫描: 15 篇
#   - 00-总览与导航.md | webman-curd-admin · 总览与导航 | 8 节
#   ...
# 输出: docs/index.html (3xx.x KB)
```

> 脚本依赖 `marked`。若提示 `Cannot find module 'marked'`，把 `NODE_PATH` 指向已装
> marked 的 node_modules 目录再跑：
> `NODE_PATH=/path/to/node_modules node tools/build_docs.cjs`

### 7.2 写作约定

| 约定 | 说明 |
|---|---|
| 文件名 | `NN-主题.md`，**编号决定顺序**；分区按编号段：`00–09` 入门与指南、`10–19` 使用指南、`20–29` API 参考 |
| 标题 | 每篇第一个 `H1` 是文档标题（左侧栏目显示它），`H2/H3` 自动生成嵌套目录树 |
| 互链 | `[标题](NN-主题.md)` 或 `[标题](NN-主题.md#小节锚点)`；文档站会接管为「切面板 + 定位小节」，GitHub 上是普通文件链接 |
| 代码块 | 用 ` ```php ` / ` ```bash ` 标注语言；文档站自动加「复制」按钮 |
| 新增文档 | 丢进 `docs/` 重跑脚本即并入左侧栏目，无需改代码（除非要开新分区，改 `build_docs.cjs` 的 `SECTIONS`） |

### 7.3 三种分发方式

| 方式 | 说明 |
|---|---|
| 本地 / 离线 | 直接双击 `docs/index.html`，零依赖、无需服务器 |
| 随发布包 | `scripts/release-zip.sh` 已把 `docs/` 与 `INSTALL.md` 打进 zip（排除 `_legacy/`） |
| 在线站点 | 仓库 → Actions → **docs-pages** → Run workflow，把 `docs/` 发到 GitHub Pages（需先在 Settings → Pages 把 Source 设为 "GitHub Actions"；私有仓库需 Pro/Team/Enterprise 才允许 Pages） |

> `docs/.nojekyll` 是给 GitHub Pages 用的，避免下划线开头的目录被 Jekyll 忽略。

> 其它都是插件自带、随包升级整体替换的。
