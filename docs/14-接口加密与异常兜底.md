# 接口加密与异常兜底

两个「线上必备」的可选项：**请求体加密**（防明文抓包 / 篡改）与**未捕获异常统一兜底**
（防堆栈泄漏，同时给用户一个可报障的编号）。

---

## 1. 接口加密（RSA + AES 信封）

### 1.1 三种模式（前端 `VITE_API_ENCRYPT`）

| 取值 | 含义 | 产物里内嵌公钥？ | 适用 |
|---|---|---|---|
| 不配 / `false` | 明文直连（**默认**，内置产物就是这版） | 否 | 内网、同机部署、不想折腾 |
| `auto` | **由后端决定**：启动时握手拿公钥，后端开着才加密 | **否** | **推荐**：同一份产物可部署到任意项目 |
| `true` | 强制加密：构建期内嵌目标宿主公钥 | 是 | 老流程 / 后端禁用了握手 |

> `auto` 的关键收益：**前端不再绑定宿主密钥**。导出项目 → 部署到新服务器 →
> 后端重新生成 key → 前端启动时自动拿到新公钥，不需要重新 `npm run build`。

### 1.2 公钥从哪来（运行时握手）

前端启动即请求（免鉴权、免加密）：

```http
GET /api/config/crypto
```

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "enabled": true,
    "handshake": true,
    "algorithm": "RSA-2048/AES-256-CBC",
    "public_key": "-----BEGIN PUBLIC KEY-----\nMIIB...\n-----END PUBLIC KEY-----",
    "fingerprint": "f646e10936ace1ff"
  }
}
```

| 字段 | 说明 |
|---|---|
| `enabled` | 后端是否开着加密（`.env` 的 `API_ENCRYPT`）。为 `false` 时前端**自动退回明文**，不会硬加密 |
| `handshake` | 后端是否允许下发公钥（`config/plugin.curd/crypto.php` 的 `handshake`） |
| `public_key` | 当前宿主的公钥 PEM；`handshake=false` 时为空串 |
| `fingerprint` | 公钥指纹（sha256 前 16 位），排查「产物里内嵌的是旧公钥」用 |

公钥取值顺序（后端）：`config/keys/api_rsa_public.pem` → 由私钥现场推导
（`openssl_pkey_get_details`，公钥文件被删/漏同步也能工作）。

前端取值顺序：**握手结果** → `VITE_API_RSA_PUBLIC_KEY` → 源码内嵌兜底值。

> 为什么可以明文下发：公钥本就是公开信息（等价于 HTTPS 证书）。真正的秘密是私钥，
> 它只留在后端 `config/keys/api_rsa_private.pem`（`0600`，已 gitignore）。

### 1.3 推荐开启方式（`auto`，不绑定宿主）

```bash
cd <插件仓库>
VITE_API_ENCRYPT=auto \
  bash scripts/build-frontend.sh <前端源码目录>
```

脚本行为：不内嵌任何宿主公钥，只校验产物里同时存在加密分支（`X-Encrypt-Data`）
与握手接口（`/api/config/crypto`），对不上直接报错不落盘。

后端侧只需保证 `.env` 里 `API_ENCRYPT` 不为 `false`（默认就是 `true`）。

### 1.4 强制模式（`true`，产物自带公钥）

```bash
VITE_API_ENCRYPT=true \
CURD_PUBLIC_DIR=<宿主>/plugin/curd/public \
  bash scripts/build-frontend.sh <前端源码目录>
```

脚本会读 `CURD_PUBLIC_DIR/../config/keys/api_rsa_public.pem` 内联进产物，并在回灌前
**校验产物里真的带上了这把公钥**，对不上直接报错不落盘。

> `true` 模式下前端**仍然会握手**：握手成功就用后端下发的公钥（永远最新），
> 只有握手失败（跨域被拦、后端关了握手）才回退到内嵌公钥。

手动构建时：

```bash
VITE_API_ENCRYPT=true \
VITE_API_RSA_PUBLIC_KEY="<api_rsa_public.pem 的内容；换行可写字面 \n>" \
  npm run build
```

### 1.5 换 key 不用重发前端（自愈重试）

后端解密失败时会回一个标记头：

```http
X-Crypto-Key-Mismatch: 1
```

前端收到后：作废本地公钥 → 重新 `GET /api/config/crypto` → 用新公钥重新加密 →
**自动重试一次**（用户无感）。所以下列场景都能自愈：

- 后端重装 / 手动换了密钥对；
- 产物里内嵌的是旧宿主的公钥；
- 同一份产物被部署到了新项目。

跨域部署时该头已在 `Access-Control-Expose-Headers` 里放开（`CorsMiddleware`）。

> 想彻底禁止下发公钥：`.env` 设 `API_CRYPTO_HANDSHAKE=false`。此时接口只回
> `enabled` 状态、`public_key` 为空串，前端只能靠内嵌公钥（等价于老行为）。

### 1.6 前后端开关对照

| 端 | 开关 | 默认 | 生效时机 |
|---|---|---|---|
| 前端 | `VITE_API_ENCRYPT` = 空 / `false` / `auto` / `true` | 空（明文） | 构建期内联 |
| 后端 | `API_ENCRYPT`（`.env`） | `true`（能解密） | 启动时 |
| 后端 | `API_CRYPTO_HANDSHAKE`（`.env`） | `true`（下发公钥） | 启动时 |

后端默认「能解就解、明文透传」，所以**前端不开也能跑**；`auto` 模式还会自动跟随
后端开关，不存在「一边开一边关」的半吊子状态。

### 1.7 豁免清单（无需配置，始终明文）

- `OPTIONS` 预检请求；
- 非 `/api` 路径（页面、静态资源）；
- `GET /api/config/crypto`（握手接口，前端此时还没有公钥）；
- `multipart` 上传（`FormData`）；
- 非 JSON 响应（CSV 导出等文件流）。

## 2. 接口异常兜底

SQL 报错、类型错误等**未捕获异常**的统一出口，由插件自带的
`plugin\curd\app\exception\CurdExceptionHandler` 负责。

### 2.1 为什么是异常处理器，不是中间件

webman 的中间件链在**每一层内层都先 `try/catch` 再转 Response**，外层中间件
**永远捕获不到**控制器 / 路由中间件抛出的异常。所以兜底只能做成异常处理器（实测踩过）。

### 2.2 生效范围

| 范围 | 怎么生效 |
|---|---|
| **插件路由**（`/api/auth/*`、`/api/curd/*`、`/api/admin/*`、`/api/menu/*` …） | **开箱生效**：插件自带 `plugin/curd/config/exception.php`，框架按 `plugin.curd.exception` 读取 |
| **宿主自己的 `/api` 控制器** | 把宿主 `config/exception.php` 的 `''` 键指向插件处理器（见下） |

```php
// config/exception.php
return [
    '' => \plugin\curd\app\exception\CurdExceptionHandler::class,
];
```

> ⚠️ 只加 `'@'` 键**无效** —— 框架规则是「本 app 配置里已有 `''` 键 ⇒ 忽略 `'@'`」，
> 而 webman 骨架默认自带 `'' => support\exception\Handler::class`。

只兜 `/api`；非 `/api` 请求任何模式下都沿用框架默认错误页 / 调试页。

### 2.3 两档模式

由 `.env` 的 `APP_DEBUG` 决定（`plugin.curd.app.debug` 读它）：

| 模式 | 行为 |
|---|---|
| `true`（默认，**本地**） | 异常信息**原样暴露**：JSON 请求返回真实 msg + traces，其余返回调试页 —— 当场可查 |
| `false`（**线上**） | `/api` 返回 **HTTP 500** `{"code":500,"msg":"服务内部错误（编号 xxxxxxxx）"}`；异常类 / 消息 / **SQL + 绑定** / 请求上下文 / 堆栈写 `runtime/logs/webman.log` |

- 宿主自己控制器的模式取宿主 `config/app.php` 的 `debug`，与插件 debug **取交集**
  （任一为 `false` 即按线上处理），线上记得两边都关；
- 响应刻意用 **HTTP 500** 而非 200：便于 Nginx / 监控按 5xx 告警；前端已能解密并展示
  非 2xx 的加密错误响应（`request.js` 的 error 分支）；
- 提示文案可改：`config/curd-admin.php` 或插件 `config/curd.php` 的 `error_message`。

### 2.4 日志刻意做成「一条异常一行」

`trace_str` 里的换行已收敛成 ` | `，且 `sql` / `bindings` 等关键字段排在堆栈**之前**。
原因是 webman 默认日志格式器开了 `allowInlineLineBreaks`，多行堆栈会把后面的字段顶到
几十行开外，`grep <编号>` 就只能看到第一行。收敛后可放心用 `grep` / `jq` / 采集器解析。

> 若你 `grep <编号>` 只看到半条，说明用的是旧版 `CurdExceptionHandler`，重新同步一次插件。

### 2.5 前端提示里的编号 = 报障凭据

```
服务内部错误（编号 a1b2c3d4）
```

```bash
grep a1b2c3d4 runtime/logs/webman.log
```

即可看到异常类、消息、SQL 与绑定。这与 `PermissionCheck` 的 403 编号是**同一套排查方式**：
403 只给编号（不泄露权限结构），`reason` 写日志，同样用编号 grep。
