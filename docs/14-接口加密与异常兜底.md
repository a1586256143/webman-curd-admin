# 接口加密与异常兜底

两件「线上必备」的事：**请求体加密**（防明文抓包 / 篡改，**默认开启**）与**未捕获异常统一兜底**
（防堆栈泄漏，同时给用户一个可报障的编号）。

---

## 1. 接口加密（RSA + AES 信封）

### 1.1 三种模式（前端 `VITE_API_ENCRYPT`）

| 取值 | 含义 | 产物里内嵌公钥？ | 适用 |
|---|---|---|---|
| **不配 / `auto`（默认）** | **由后端决定**：启动时握手拿公钥，后端开着才加密 | **否** | **发行产物就是这版**：同一份 dist 可部署到任意项目 |
| `true` | 强制加密：构建期内嵌目标宿主公钥 | 是 | 老流程 / 后端禁用了握手 |
| `false` / `off` | 明文直连 | 否 | 确有不方便加密的客户端时才用 |

> **为什么默认就是 auto**：插件对外只发打包好的 dist，**用户拿不到前端源码、没法自己 build**。
> 所以「加密与否」不能交给用户在构建期决定，只能让产物在运行时问后端要公钥：
> 后端开着就加密，后端关了就明文。同一份产物因此能装到任何项目，包括后端重新生成
> key 的新部署 —— 不需要重新打包。
>
> `auto` 的关键收益：**前端不再绑定宿主密钥**。导出项目 → 部署到新服务器 →
> 后端重新生成 key → 前端启动时自动拿到新公钥。

### 1.2 公钥从哪来（运行时握手）

前端启动即请求（免鉴权、免加密）：

```http
GET /api/config/crypto
```

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "enabled": true,
    "handshake": true,
    "algorithm": "RSA-2048/AES-256-CBC",
    "public_key": "-----BEGIN PUBLIC KEY-----\nMIIB...\n-----END PUBLIC KEY-----",
    "fingerprint": "f646e10936ace1ff"
  }
}
```

| 字段 | 说明 |
|---|---|
| `enabled` | 后端是否开着加密。默认 **`true`**（dev / prod 一致），只有显式关闭才是 `false`；为 `false` 时前端**自动退回明文**，不会硬加密 |
| `handshake` | 后端是否允许下发公钥（`config/plugin.curd/crypto.php` 的 `handshake`） |
| `public_key` | 当前宿主的公钥 PEM；`handshake=false` 时为空串 |
| `fingerprint` | 公钥指纹（sha256 前 16 位），排查「产物里内嵌的是旧公钥」用 |

公钥取值顺序（后端）：`config/keys/api_rsa_public.pem` → 由私钥现场推导
（`openssl_pkey_get_details`，公钥文件被删/漏同步也能工作）。

前端取值顺序：**握手结果** → `VITE_API_RSA_PUBLIC_KEY` → 源码内嵌兜底值。

> 为什么可以明文下发：公钥本就是公开信息（等价于 HTTPS 证书）。真正的秘密是私钥，
> 它只留在后端 `config/keys/api_rsa_private.pem`（`0600`，已 gitignore）。

### 1.3 发行默认：`auto`（不用传任何构建参数）

```bash
cd <插件仓库>
bash scripts/build-frontend.sh <前端源码目录>      # 默认就是 auto
```

脚本行为：不内嵌任何宿主公钥，只校验产物里同时存在加密分支（`X-Encrypt-Data`）
与握手接口（`/api/config/crypto`），对不上直接报错不落盘。

后端侧什么都不用配：`plugin/curd/config/crypto.php` 的 `enabled` 默认就是 `true`，
`handshake` 也默认 `true`，安装时 `install.php` 会生成密钥对 —— 装完即加密。

### 1.4 强制模式（`true`，产物自带公钥）

```bash
VITE_API_ENCRYPT=true \
CURD_PUBLIC_DIR=<宿主>/plugin/curd/public \
  bash scripts/build-frontend.sh <前端源码目录>
```

脚本会读 `CURD_PUBLIC_DIR/../config/keys/api_rsa_public.pem` 内联进产物，并在回灌前
**校验产物里真的带上了这把公钥**，对不上直接报错不落盘。

> `true` 模式下前端**仍然会握手**：握手成功就用后端下发的公钥（永远最新），
> 只有握手失败（跨域被拦、后端关了握手）才回退到内嵌公钥。

手动构建时：

```bash
VITE_API_ENCRYPT=true \
VITE_API_RSA_PUBLIC_KEY="<api_rsa_public.pem 的内容；换行可写字面 \n>" \
  npm run build
```

### 1.5 换 key 不用重发前端（自愈重试）

后端解密失败时会回一个标记头：

```http
X-Crypto-Key-Mismatch: 1
```

前端收到后：作废本地公钥 → 重新 `GET /api/config/crypto` → 用新公钥重新加密 →
**自动重试一次**（用户无感）。所以下列场景都能自愈：

- 后端重装 / 手动换了密钥对；
- 产物里内嵌的是旧宿主的公钥；
- 同一份产物被部署到了新项目。

跨域部署时该头已在 `Access-Control-Expose-Headers` 里放开（`CorsMiddleware`）。

> 想彻底禁止下发公钥：`.env` 设 `API_CRYPTO_HANDSHAKE=false`。此时接口只回
> `enabled` 状态、`public_key` 为空串，前端只能靠内嵌公钥（等价于老行为）。

### 1.6 前后端开关对照

| 端 | 开关 | 默认 | 生效时机 |
|---|---|---|---|
| 前端 | `VITE_API_ENCRYPT` = 不配 / `auto` / `true` / `false` | **不配 = `auto`** | 构建期内联 |
| 后端 | `curd-admin.php` 的 `api_encrypt` | 不写 = 跟随下一行 | 启动时（优先级最高） |
| 后端 | `API_ENCRYPT`（`.env`） | **`true`**（dev / prod 一致） | 启动时 |
| 后端 | `API_CRYPTO_HANDSHAKE`（`.env`） | `true`（下发公钥） | 启动时 |

**要关闭加密，只需显式写一个开关**（二者选一，写完 restart）：

```php
// config/curd-admin.php
return [
    'api_encrypt' => false,   // 关掉接口加密（明文直连）
];
```

```dotenv
# .env
API_ENCRYPT=false
```

关掉后：后端中间件完全透传（明文请求照常、密文不再解密），前端 `auto` 模式握手
拿到 `enabled:false` 也会同步退回明文 —— 不需要重新打包前端。

> 为什么默认开而不是默认关：加密的收益是防明文抓包/篡改，代价已经由「运行时握手」
> 抹平了（不会因为换 key 而全线 400）。所以 dev 与 prod 统一默认开，行为一致、
> 少一类「本地能用线上不能用」的排查。

### 1.7 豁免清单（无需配置，始终明文）

- `OPTIONS` 预检请求；
- 非 `/api` 路径（页面、静态资源）；
- `GET /api/config/crypto`（握手接口，前端此时还没有公钥）；
- `multipart` 上传（`FormData`）；
- 非 JSON 响应（CSV 导出等文件流）。

### 1.7.1 中间件挂在哪（宿主零配置）

加解密中间件 **由插件自带**，宿主 `config/middleware.php` **不用改**：

```php
// plugin/curd/config/middleware.php（插件内，随插件自动加载）
return [
    'plugin.curd' => [\plugin\curd\app\middleware\ApiCrypto::class],
];
```

- 键名必须是 `'plugin.curd'`：webman 的 `Middleware::load()` 解析 `'plugin.{名}'` 才是
  「该插件的全部路由」；写 `''` 只作用于默认 app，插件路由拿不到。
- 覆盖范围 = 插件全部 `/api/*`（`/api/auth/*`、`/api/curd/*`、`/api/admin/*`、
  `/api/menu/*`、`/api/config/*`、`/api/curd/model/{model}/*`）。
- 宿主自建接口（控制器不在 `plugin\curd\...` 命名空间下）才需要宿主自己挂一次；
  两边都挂也**不会重复加解密** —— 中间件内有请求级幂等标记 `apiCryptoHandled`，
  同一条请求只处理一次（否则响应会被包两层，前端解出来还是 `ENC1:` 信封）。
- 顺序：插件级中间件比路由中间件（Cors / AuthCheck / PermissionCheck）更靠外，
  所以鉴权失败的 401 也会被加密，与正常响应一致。

### 1.8 密钥怎么来（装完即用，四种方式）

| 场景 | 做法 |
|---|---|
| **composer 安装 / 更新**（最常见） | **不用管**：`composer require amcolin/webman-curd-admin` 结束时会自动执行 `php plugin/curd/keygen.php` 生成密钥 |
| 命令行单独生成 / 检查 | `php webman curd:crypto-key`（webman console 命令） |
| 脱离框架（连 composer 都没装好） | `php plugin/curd/keygen.php`（纯 openssl 独立脚本） |
| Web 安装向导 / `install.php` | 向导第 D 步自动生成（`Install::ensureKeys()`，已前移到建库之前） |

composer 阶段的行为（`src/Install.php` 的 `ensureCryptoKeys()`，由宿主的
`post-package-install` / `post-package-update` → `support\Plugin::install` 触发）：

```
  [webman-curd-admin] 接口加密密钥已就绪（plugin/curd/config/keys/，私钥请单独备份、勿提交 git）
  [webman-curd-admin] 若 webman 正在运行，请 restart 让新私钥生效
```

- 密钥已存在 → **跳过**（幂等，绝不覆盖正在用的私钥；换密钥要显式 `--force`）；
- 宿主显式关闭加密（`config/curd-admin.php` 的 `'api_encrypt' => false` 或 `.env` 的
  `API_ENCRYPT=false`）→ **跳过**，不生成没人用的密钥；
- 想临时跳过：`CURD_SKIP_KEYGEN=1 composer require ...`；
- 生成失败（openssl 缺失 / 目录不可写）**不阻断安装**，只打警告，之后手动跑一次即可；
- 覆盖安装时 `config/keys/` 会被**完整保留**（不会被新包里的空目录冲掉）。

四条命令共用同一份实现（`plugin/curd/app/CryptoKeys.php`），参数一致：

```bash
php plugin/curd/keygen.php                 # 生成 RSA-2048（已存在则跳过）
php plugin/curd/keygen.php --force         # 强制换一对（旧密文将无法解密）
php plugin/curd/keygen.php --bits=4096     # 指定位数
php plugin/curd/keygen.php --show          # 只看状态 + 公钥指纹，不生成
php plugin/curd/keygen.php --print-public  # 额外打印公钥 PEM（要内嵌进前端时用）

# webman console 里是同一套参数
php webman curd:crypto-key --show
```

输出位置（可用 `config/crypto.php` 的 `private_key_path` / `public_key_path` 改）：

```
plugin/curd/config/keys/api_rsa_private.pem   0600  私钥 —— 永不外发，勿提交 git
plugin/curd/config/keys/api_rsa_public.pem    0644  公钥 —— 可公开，前端握手读取
```

幂等与自愈规则：

- 两个文件都在 → **跳过**（绝不悄悄覆盖，否则已加密的请求全废）；
- 只有私钥（公钥被删/漏同步）→ **只从私钥推导补出公钥**，私钥不动；
- 私钥缺失（公钥单独存在也没用）→ 重新生成一对；
- 生成后**已在运行的进程要 restart**（私钥在进程内静态缓存）。

### 1.9 前端能看到什么、看不到什么

| 内容 | 前端产物里有没有 | 说明 |
|---|---|---|
| **私钥** | **没有**（也永远不会有） | 只在后端 `config/keys/api_rsa_private.pem`，`0600` |
| **公钥** | **没有** | 运行时 `GET /api/config/crypto` 拿，用完只存在内存 |
| 密钥文件本身 | 没有 | 后端从磁盘读，前端拿不到文件 |
| 加密算法代码 | 有 | **这是无法隐藏的**：浏览器必须能执行它 |

> 一句话：**密钥可以不给前端，算法不行**。浏览器端加密永远无法对「使用这个浏览器的人」
> 隐藏实现（JS 可读、可断点、可改）。所以本方案的定位是「防抓包/防篡改」，
> 不是「防前端开发者」。真要防止内容被看到，靠的是 HTTPS + 后端鉴权，不是前端加密。
>
> 想进一步减少可见面：发行产物（`VITE_API_ENCRYPT` 默认 `auto`）**不内嵌任何密钥**，
> 全量 `public/assets` 里搜不到 `BEGIN PUBLIC KEY`；要连算法库都不想出现在主包，
> 可以自行把 `crypto-js` / `jsencrypt` 改成动态 `import()` 拆成独立 chunk（仍是可下载的，
> 只是不在首屏包里）。

### 1.10 响应也加密（为什么有时候看不到密文）

信封加密是**对称**的：AES 密钥由前端**每次请求**随机生成，用 RSA 公钥包一层带给后端。
后端把响应加密回去，用的就是**这次请求带来的那把 AES 密钥** —— 于是：

| 本次请求 | 后端手里有 AES 密钥吗 | 响应 |
|---|---|---|
| 带信封（正常情况） | 有 | **加密**：`{"data":"ENC1:<iv>.<cipher>"}`，响应头 `X-Crypto-Encrypted: 1` |
| 明文（`off` 模式 / 握手失败 / 豁免清单里的接口） | 没有 | **只能明文** —— 没密钥可用，这不是 bug |

> 这也是为什么「响应没加密」几乎总是意味着「这次请求本身就没加密」：
> 后端不会凭空知道前端打算用什么密钥。

不会被加密的响应（与请求豁免同一份清单）：

- 非 `application/json`：CSV / Excel 导出、文件下载、`text/html` 错误页；
- `204` 空体响应；
- 豁免清单里的接口（握手、验证码等，见 §1.7）。

前端拿到密文后由响应拦截器**统一解密**（成功与失败分支都处理），业务代码拿到的仍是
普通 JSON —— 唯一区别是 DevTools 里看到的是 `ENC1:...`。

### 1.11 排查「到底加密了没有」

**第一步：看响应头，别看 body 长相**

DevTools → Network → 任选一个 `/api` 请求：

- Request Payload / Query 是 `ENC1:...` → 请求已加密；
- Response Headers 有 `X-Crypto-Encrypted: 1` → 响应已加密；
- 两个都没有 → 这一路全程明文，继续第二步。

**第二步：控制台看状态**（任意页面可用，不需要页面有 customJs）

```js
curdCrypto.status()
// { mode: 'auto', active: true, ready: true, hasKey: true, fingerprint: '79cb3811c2c9268a' }
```

| 字段 | 含义 | 异常时的原因 |
|---|---|---|
| `mode` | 构建时的 `VITE_API_ENCRYPT`：`off` / `auto` / `true` | `off` → 打包时显式关掉了加密 |
| `active` | 当前是否真的在加密 | `false` → `mode=off`，或握手明确告知后端已关闭 |
| `ready` | `null`=未握手 / `true`=已生效 / `false`=退回明文 | `false` → 后端 `enabled=false`（`api_encrypt=false` / `API_ENCRYPT=false`） |
| `hasKey` | 是否已拿到公钥 | `false` → 握手 404/500、CORS 未放行该接口、或 `handshake=false` 且产物没内嵌公钥 |

**第三步：对指纹**

```bash
php webman curd:crypto-key --show     # 后端当前私钥对应的公钥指纹
```

与 `curdCrypto.status().fingerprint` 不一致 → 进程还在用旧私钥（私钥在进程内缓存），
`restart` 后再看。换密钥后想立刻生效又不想刷新页面：

```js
await curdCrypto.handshake()   // 丢掉旧公钥重新握手，之后请求自动用新密钥
```

## 2. 接口异常兜底

SQL 报错、类型错误等**未捕获异常**的统一出口，由插件自带的
`plugin\curd\app\exception\CurdExceptionHandler` 负责。

### 2.1 为什么是异常处理器，不是中间件

webman 的中间件链在**每一层内层都先 `try/catch` 再转 Response**，外层中间件
**永远捕获不到**控制器 / 路由中间件抛出的异常。所以兜底只能做成异常处理器（实测踩过）。

### 2.2 生效范围

| 范围 | 怎么生效 |
|---|---|
| **插件路由**（`/api/auth/*`、`/api/curd/*`、`/api/admin/*`、`/api/menu/*` …） | **开箱生效**：插件自带 `plugin/curd/config/exception.php`，框架按 `plugin.curd.exception` 读取 |
| **宿主自己的 `/api` 控制器** | 把宿主 `config/exception.php` 的 `''` 键指向插件处理器（见下） |

```php
// config/exception.php
return [
    '' => \plugin\curd\app\exception\CurdExceptionHandler::class,
];
```

> ⚠️ 只加 `'@'` 键**无效** —— 框架规则是「本 app 配置里已有 `''` 键 ⇒ 忽略 `'@'`」，
> 而 webman 骨架默认自带 `'' => support\exception\Handler::class`。

只兜 `/api`；非 `/api` 请求任何模式下都沿用框架默认错误页 / 调试页。

### 2.3 两档模式

由 `.env` 的 `APP_DEBUG` 决定（`plugin.curd.app.debug` 读它）：

| 模式 | 行为 |
|---|---|
| `true`（默认，**本地**） | 异常信息**原样暴露**：JSON 请求返回真实 msg + traces，其余返回调试页 —— 当场可查 |
| `false`（**线上**） | `/api` 返回 **HTTP 500** `{"code":500,"msg":"服务内部错误（编号 xxxxxxxx）"}`；异常类 / 消息 / **SQL + 绑定** / 请求上下文 / 堆栈写 `runtime/logs/webman.log` |

- 宿主自己控制器的模式取宿主 `config/app.php` 的 `debug`，与插件 debug **取交集**
  （任一为 `false` 即按线上处理），线上记得两边都关；
- 响应刻意用 **HTTP 500** 而非 200：便于 Nginx / 监控按 5xx 告警；前端已能解密并展示
  非 2xx 的加密错误响应（`request.js` 的 error 分支）；
- 提示文案可改：`config/curd-admin.php` 或插件 `config/curd.php` 的 `error_message`。

### 2.4 日志刻意做成「一条异常一行」

`trace_str` 里的换行已收敛成 ` | `，且 `sql` / `bindings` 等关键字段排在堆栈**之前**。
原因是 webman 默认日志格式器开了 `allowInlineLineBreaks`，多行堆栈会把后面的字段顶到
几十行开外，`grep <编号>` 就只能看到第一行。收敛后可放心用 `grep` / `jq` / 采集器解析。

> 若你 `grep <编号>` 只看到半条，说明用的是旧版 `CurdExceptionHandler`，重新同步一次插件。

### 2.5 前端提示里的编号 = 报障凭据

```
服务内部错误（编号 a1b2c3d4）
```

```bash
grep a1b2c3d4 runtime/logs/webman.log
```

即可看到异常类、消息、SQL 与绑定。这与 `PermissionCheck` 的 403 编号是**同一套排查方式**：
403 只给编号（不泄露权限结构），`reason` 写日志，同样用编号 grep。
